RESOLVED — fixed in eedc875 (fork→spawn)

I have a Python 3.9 background worker service (systemd, long-running, `Restart=on-failure`) that polls a remote server over SSH every 5 seconds in an infinite loop. Each poll cycle calls `subprocess.run(argv, input=raw, stdout=subprocess.PIPE, stderr=subprocess.PIPE, timeout=30, check=False)` to talk to the remote server (a custom SSH-stdio JSON-RPC transport, one fresh SSH connection per call).

When a job requiring real work arrives, the worker executes it via `multiprocessing.get_context("fork").Process(...)`, forking a child that runs a handler function and sends the result back over a `multiprocessing.Pipe`. The parent enforces a timeout with `parent_conn.poll(timeout_seconds)`, and on timeout calls `process.terminate()` then `process.kill()` if still alive.

**Symptom:** This works perfectly every time when run as a one-shot script (`python3 myworker.py --once`, does one poll cycle then exits). But when the SAME code runs under the persistent systemd service (thousands of poll cycles over many hours before the job arrives), the fork sometimes hangs forever with **zero exceptions, zero log output, no crash, no restart** — the parent process's own polling loop looks completely healthy afterward (no orphaned child process ever appears via `pgrep -P <parent_pid>` in my monitoring), but the job itself never completes and no error is ever raised anywhere up the call stack, including inside a `try/except Exception` wrapping the whole per-iteration loop body that reliably logs any other kind of failure to stderr.

I've ruled out: process crashes/restarts (same PID for the service's whole uptime), credential/token expiry (stateless, wall-clock-based, no caching), a leftover/duplicate worker process (confirmed only one process running), and a genuinely stuck child staying alive for the observation window (none observed).

My working hypothesis: `subprocess.run()` with both `stdout=PIPE` and `stderr=PIPE` internally spins up short-lived background reader threads (CPython's `Popen.communicate()` implementation) to drain both pipes concurrently without deadlocking on OS pipe buffers. Since the long-lived service calls `subprocess.run()` this way thousands of times before ever reaching the `fork()` call, there's a nonzero chance one of these background threads is still alive (mid-teardown, possibly holding some internal lock — I/O buffer lock, allocator lock, etc.) at the exact instant `multiprocessing.get_context("fork").Process().start()` forks. A one-shot script does at most 1-2 such subprocess calls before its single fork, so the race almost never lands there, but it's nearly guaranteed to eventually land in the long-running service. `fork()` only copies the calling thread; if another thread held a lock at fork time, the child inherits that lock in a permanently-locked state with no thread left alive to release it — the child can deadlock on its very first attempt to touch that lock (e.g. writing to a pipe, or even just interpreter-internal bookkeeping), silently, forever, never reaching any of its own error-handling code.

Questions:
1. Is this a real, known CPython hazard (`subprocess` background reader threads + `fork()`-based `multiprocessing` in a long-lived process)? Is my mechanism right, or is there a more likely explanation for "hangs only after many fork-free `subprocess.run()` calls in a long-lived process, never on a fresh short-lived process, with zero exceptions anywhere"?
2. What's the standard, well-established fix — switching `multiprocessing.get_context("fork")` to `"spawn"` or `"forkserver"`? Are there other established mitigations (e.g., `os.register_at_fork()` hooks, avoiding dual-PIPE `subprocess.run()`, isolating the SSH subprocess calls onto a dedicated always-running process instead of ad hoc per-call)?
3. What's the fastest way to *empirically confirm* this specific hypothesis on a live Linux service before committing to a fix — e.g., logging `threading.active_count()`/`threading.enumerate()` immediately before every `Process().start()` call, or something more direct like `faulthandler`/`py-spy dump` on a hung child if I can catch one in the act?
